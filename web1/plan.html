The five moves, and the reasoning behind each
Move 01
Publish a registry, not a gallery

Sixty projects, each on its own URL, filtered by industry, region, type and year, with every filtered view shareable as a link.

Why it wins: It converts a private track record into a public asset that works while nobody is selling. It also compounds: sixty pages ranking for sixty specific searches, against a field where one page carries everything.
  1. Agree the published field set with IAQ, scope and location only, never client names.
  2. Build the project template once, then fill it sixty times.
  3. Ship the four filters and write every state to the URL.
  4. Add the shortlist so a buyer can gather projects and attach them to an enquiry.
  5. Measure which filters get used, and lead the next content round with the answer.
Move 02
Publish the numbers nobody else publishes

Cleanroom class, area in square metres, systems delivered, completion year, on every project page, set in monospace so a buyer can compare down a column.

Why it wins: Zero firms in the audit publish cleanroom class. This is the single hardest thing for a competitor to copy, because it requires the delivery record to actually exist and be organised. Marketing budget cannot substitute for it.
  1. Pull the specification data from project records, not from memory.
  2. Agree with legal what can be published per project.
  3. Where a value cannot be published, publish the range or state that it is under NDA.
  4. Never publish a figure that has no source, since one wrong number discredits the other fifty nine.
Move 03
Make the proof travel without us

A gated capability and certification pack, a shortlist link that carries the projects a buyer viewed, and a specification block a champion can forward internally.

Why it wins: A cleanroom package is bought by a committee, not a person. The site wins when the one person who likes IAQ can sell it to five who have never heard of it. Every competitor forces that conversation to start from zero.
  1. Build the gate once and use it twice, for the capability pack and for Investor Relations.
  2. Route every enquiry by intent to a named owner, never a shared inbox.
  3. Attach the shortlist to the enquiry so the first reply already knows what they looked at.
  4. Give the champion a link, a PDF and a specification they can paste into an internal paper.
Move 04
Show what is inside the facility

The cross-section hero and the systems layers, in real 3D, revealing the eight systems IAQ delivers inside a building most people never see the inside of.

Why it wins: It explains the product in five seconds where a paragraph fails, and it is the one place where craft is visible. The trap it avoids is decoration: every 3D element here carries an explanation, so it survives the technical buyer rather than annoying them.
  1. One scene definition drives the homepage hero, the capability pages and the 360 viewer.
  2. Every 3D element carries a caption naming what is shown.
  3. Cut anything that cannot survive that caption test.
  4. Ship a complete static state for reduced motion and slow connections.
Move 05
Build four routes, not one funnel

The facility buyer, the engineer, the investor and the partner each get their own path, their own entry pages and their own single ask.

Why it wins: The site is carrying a listing, a hiring programme and a sales pipeline at once. Competitors run one generic funnel and lose three audiences to serve one. Separating them costs nothing at build time and is close to impossible to retrofit.
  1. Write the four routes into the structure before any page is designed, as part 04 does.
  2. One ask per route, never two competing buttons.
  3. Give each route a real entry page, since search drops people deep and not on the homepage.
  4. Track each route separately from launch so the next investment is decided by data.

The layout grid
Desktop12 columns, 1320px maximum

Content sits in 12 columns with a 24px gutter. Reading text never exceeds 8 columns, so a paragraph stays under about 75 characters and stays readable at any window width.

Tablet8 columns

Two-up card rows collapse before three-up rows do, so a card never falls below 280px and becomes unreadable.

Mobile4 columns, one card per row

Every table scrolls inside its own container. The page body never scrolls horizontally, at any breakpoint, on any page.

Spacing is a scale, not a judgement. 4, 8, 12, 16, 24, 32, 48, 64, 96. Every margin and padding in the build comes from that list. A value outside it is a bug, not a preference, and it is the single rule that keeps thirty pages built by different hands looking like one site.
The component library
01Section band

A full-width ground with a white content card inside it. Alternating grounds separate chapters without needing a coloured bar or a divider graphic.

02Figure counter

A measured number in monospace with its unit and its qualifier underneath. Used for years, projects, offices, area and manhours. Never used for a number we cannot source.

03Project card

Photograph, scope, sector, location, year, cleanroom class where applicable. Identical on the registry, on similar-project rows and in the shortlist.

04Specification block

A two-column table of measured values, monospace, on the project page. This is the component the technical buyer actually reads.

05Filter bar

Industry, region, type and year, plus a result count and a clear-all. Every state writes to the URL.

06Shortlist control

A save toggle on every project card and a persistent counter in the header. The shortlist is the bridge between browsing and the enquiry.

07The ask

One primary button per page, always the same size, weight and colour. Secondary routes are text links, never a second button of equal weight.

08Gate

The pattern behind the capability pack and Investor Relations: a short form or a passcode, then the content. Used twice, built once.

09Systems layer

The 3D component that reveals what sits inside a facility. Appears on the homepage hero, the capability pages and the 360 viewer, driven by one scene definition.
